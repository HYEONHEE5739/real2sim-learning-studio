## 1. 집계와 읽는 법

기준 Commit `8e02b1ae023a856694a40b947881f76b66410624`의 현재 Git 추적 소스와 AST를 직접 집계했다. 제품 Python **177개**, **37,927줄**, 함수 정의 **1,909개**, 클래스 정의 **152개**다. 함수 수는 메서드·지역 함수 포함이고 lambda는 제외한다. 클래스 수는 지역 클래스도 포함한다. 이 숫자는 모든 정의의 정적 목록이며 각 정의를 동일 깊이로 독립 검증했다는 뜻이 아니다. 주요 실행 경로는 각 장에서 Caller/Consumer까지 상세히 추적했다. 시험 Python은 **209개**다. 이번에 pytest를 수집/실행한 숫자가 아니며 이전 2,151 testcase는 parameterization을 포함한 과거 회귀 결과다.

| 중요도 | 기준 |
|---|---|
| Core | 계산·검증·데이터 계약의 중심 |
| Entry | UI/CLI/Worker의 실행 진입·dispatch |
| Integration | Qt·엔진·장치·외부 SDK/모델 연결 |
| Support | namespace·저장/경로/표시 helper |
| Test | 제품 소스와 분리한 회귀/Fixture 코드 |

아래 표의 **호출자**는 정적 import/직접 module 참조로 확인한 대표 모듈 최대2개다. Python의 모든 실제 호출을 완전하게 복원한 동적 Call Graph는 아니다. 함수 내부 lazy import도 포함되므로 참조가 있다는 사실만으로 매번 모델이 로딩된다고 해석하지 않는다. 주요 의존성의 `+N`은 표에 생략한 정적 연결 수다. 직접 역참조가 없는 모듈은 CLI/dynamic dispatch/namespace일 수 있어 “미사용”이라고 단정하지 않는다. 관련 시험은 정적 import와 파싱 가능한 내장 Qt 시험 스크립트의 참조다. 직접 참조 미확인은 통합 시험 부재의 증명이 아니다.

모든 제품 `.py` 파일을 한 행씩 포함한다. 구현 이름을 짐작해 만든 파일은 없다. 파일마다 주요 정의 링크를 제공하며, 긴 메서드/내부 helper는 source와 상세 장으로 이동해 읽는다. 정적 참조는 Runtime 성공 인증이 아니며 [검증 수준](README.md#verification-levels)과 별도다.

시험은 런타임/단위 수학/Qt/네이티브 Parser/Mock 경계를 섞지 않고 읽는다. 아래 전체 목록은 파일별 test_ 정의 개수와 대표 함수다. 파라미터 확장·fixture 실행·수집 결과를 계산한 것이 아니다. Fixture가 `/assets-private`나 과거 evidence를 참조할 수 있어 저장소만 복제한 호스트에서 그대로 재현된다고 보장하지 않는다. 이번 문서화에서 원본 사용자 자료를 열어 실행하지 않았다.

먼저 볼 시험 묶음은 ① test_stage_pipeline/Artifact/Runtime ② test_joint_camera_adaptation/acceptance/observation_refresh/final_audit_contracts ③ test_asset_view/wireframe_features/collision_xray ④ test_native_dataset/publication_visibility/conversion_cancel ⑤ test_checkpoint_config_resolution/validation_episode_lineage ⑥ test_worker_protocol/worker_exit_integration이다. 각각 상세 장에서 입력과 assertion을 해설했다.

## 7. 핵심 Caller → Callee → Consumer

| 기능 | 실제 따라갈 경계 | 상세 장 |
|---|---|---|
| 화면 시작 | run_workbench_ui.sh → ui.app.main → Window → WorkflowPage/SessionClient | [01](01-system-architecture.md) |
| Scene 입력 저장 | CapturePage.store_materials → BackendJob(session_materials) → operations.execute → session_operations.execute → scene_preparation.save_inputs → Evidence/Project → scene_details | [02](02-scene-reconstruction.md), [실습A](07-execution-and-debugging.md#debug-scene) |
| Auto Reconstruction | ReconstructionDialog → Builder CLI → automation.reconstruct → _run_stage_pipeline → Stage handler → invoke/Worker → Artifact Consumer | [02](02-scene-reconstruction.md) |
| 직접 Joint Fit | Candidate.fit → calibration.geometry.fit → joint.fit_joint_scene → scope/preserve → reproject_observations → save → cloud_inputs | [03](03-camera-assets-simulation.md), [BUG012](05-bug-fixes-explained.md#bug-012) |
| Asset 표시 | ObjectLibraryDialog → BackendJob object_library → asset_view.load_asset_view → verify/_convert → AssetViewport.upload/paintGL | [03](03-camera-assets-simulation.md#geometry-viewer) |
| Native→Learning | Native segment commit → Catalog/Curation → materialize/publish → train.freeze_inputs → official Child → seal_checkpoint → validation/evaluation | [04](04-robot-learning.md) |
| R03 종료 | cli worker --monitor → 실행 worker.execute → result/run terminal → wait → process_exit → read_status → Qt poll | [01](01-system-architecture.md#architecture-r03), [NEW03](05-bug-fixes-explained.md#new-03) |

이 표의 화살표는 관련 source line을 따라 확인한 핵심 경로다. dynamic import·모드별 branch 전체를 정적 import 표 하나로 증명하지 않는다. 예를 들어 R03의 _run_stage는 PreparedRun.stage/engine에 따라 다른 엔진 Runner를 고르고, Builder invoke는 operation에 따라 CPU/GPU child 또는 Codex를 선택한다. 과거 docstring/설치 문서보다 실제 조건과 다음 Consumer를 우선한다.

권장 전체 읽기 순서와 처음 열 코드10개는 [08장](08-glossary-and-learning-path.md#learning-ten-files)에 있다. 실제 허가된 개발 때의 CLI/로그 확인은 [07장](07-execution-and-debugging.md)으로 이동한다.
