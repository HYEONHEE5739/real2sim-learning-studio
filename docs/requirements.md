## 확정: DataGen IK는 Pinocchio DLS + Best Effort 단일 방식 — 2026-10-25

- 새 Workbench DataGen은 **Pinocchio DLS + Best Effort**만 사용한다. 사용자에게 Solver/Failure Policy를 선택하게 하지 않고, SciPy IK Solver 및 Strict/Hold 실행 분기·호환 계층·자동 fallback을 이관하지 않는다. UI 선택 위젯과 Recipe 옵션도 만들지 않는다. 이 제외는 SciPy 라이브러리의 좌표 변환·정합 등 다른 용도를 삭제하라는 뜻이 아니다.
- 기존 DLS 계산·고정 파라미터·측정 팔 관절각 seed·좌표 변환·joint order를 보존한다. 기존 Best Effort의 candidate shape/유한값/관절 제한 및 **직전 적용 명령 대비 팔 관절별 0.5 rad/step 초과 점프 거부**를 유지한다. 경계값과 내부 수치 처리는 [상세 SPEC](../SPEC-simulation-workflows.md#datagen-ik-고정-계약)을 따른다.
- 수렴 또는 pose 오차 기준 미달만으로 candidate를 거부하거나 측정 자세 Hold로 전환하지 않는다. 유효한 candidate를 적용하고, 부적합 candidate는 해당 attempt를 중단·실패 기록한다. DLS 반복 내부 관절 제한 처리는 유지하며, 최종 부적합 명령을 clipping해서 적용하지 않는다.
- DataGen 성공 데이터 채택은 기존 **latched StableGrasp AND Placement**로 판단한다. IK 수렴·candidate 적용을 Task 성공으로 간주하지 않는다. 두 판정의 계산·threshold·접촉·시간·호출 시점은 변경하지 않는다. Annotation 및 Simulation Evaluation의 기존 단계별 성공 의미도 변경하지 않는다.
- B01의 SciPy + Strict 실행·원본·실패 trace를 그대로 보존한다. 새 고정 IK로 인한 명령·궤적·실패 분류·성공률 차이는 **승인된 의도적 변경**으로 보고하며 B01과 수치·결과가 같다고 주장하지 않는다. 기존 DLS + Best Effort 계산 재사용과 B01 대비 정책 변경을 나누어 검증한다.
- 과거 Dataset/실행의 IK provenance를 새 값으로 바꾸지 않는다. 다른 IK 계약의 과거 생성 run을 새 정책의 Resume로 연결하지 않으며, 적합한 annotated 입력에서 새 run으로 시작할 수 있다. 고정 IK identity·파라미터·안전 조건·실제 진단값은 시스템이 결과에 기록한다. 이를 Recipe 선택 옵션으로 노출하지 않는다.
- 이번 승인은 **설계 반영만**을 뜻한다. IK 구현·추가 Baseline 실행·양 엔진 검증은 이번에 수행하지 않고, DataGen 구현 단계에서 계산·안전 경계·Isaac/MuJoCo 연결을 검증한다. 기존 Sim5.1/Lab2.3/LeRobot0.4.1/MuJoCo3.3.7 개발 기준을 유지한다.

## 확정: 함수 추가와 Recipe 선택을 통한 확장

- 첫 구현은 Scene v8 Pick & Place에 집중한다. 서랍이나 여러 신규 Task를 미리 구현하지 않는다.

- 제공되는 기능 범위 내의 물체 선택, 고정 초기 위치·자세, Random Reset 범위는 Python 수정 없이 Recipe로 설정한다.
- 새로운 Task 함수 추가 때문에 기존 공통 실행 코드나 UI를 반복 수정하지 않는 구조를 지향한다. 아키텍처 검토에서는 함수 추가·등록·Recipe 연결만으로 확장 가능한지 확인한다.

- Isaac Lab과 MuJoCo는 각각 공식 API와 권장 구성을 사용하되, 공통 Recipe에서 동일한 Scene Object를 참조할 수 있어야 한다. 공통 Object 참조가 두 엔진의 모든 기능·물리 동등성을 뜻하지는 않는다.
- `tasks/pick_place.py`, `tasks/drawer.py`, `object_in_drawer()`는 확장 의도를 설명하는 예시다. 실제 폴더 구조, 함수 등록 방식, Recipe 스키마는 아키텍처 설계에서 대안을 비교한 뒤 결정한다.

## 확정: Recipe 중심 Workflow와 두 엔진 실행

- 각 단계의 동작 설정은 사용자가 작성하는 Recipe를 기준으로 실행한다. 물체·Task·Reset·성공/실패 조건 등의 설정을 UI 체크박스·탭별 설정 폼으로 중복 구성하는 방식은 요구하지 않는다.
- Builder의 Scene과 Metadata를 공통 실행 구성에 연결한다. 지원 계약에 맞는 새 Scene은 Scene별 공통 실행 Python을 다시 작성하지 않고 선택한 Scene과 Recipe로 실행할 수 있어야 한다.
- 개발자는 필요한 Task 기능을 Python 함수로 구현하고 정해진 등록 위치에 이름·파라미터 계약과 함께 등록한다. 사용자는 Recipe에서 해당 기능을 참조한다. 사용자 역할이 개발자와 같을 수 있다.
- Reset, Annotation 성공·채택 조건, DataGen 성공·실패 조건, Simulation Evaluation 성공·실패 조건 등을 단계별로 구성할 수 있어야 한다. 기존 Pick & Place의 계산·상태·시점과 단계별 조건 차이는 보존한다.
- Isaac Lab과 MuJoCo를 두 실행 경로로 지원하며, Scene Object 참조와 단계별 설정에는 동일하게 약속된 Recipe 문법을 사용한다. 엔진별 환경 구성·상태 접근·물리 실행은 각 엔진의 공식 구조에 맞게 구현한다.
- 공통 실행 구성은 Recipe와 등록 기능을 해석해 실행하는 재사용 가능한 틀을 뜻한다. 모든 임의 Scene·Task를 자동 이해하거나, 한 엔진의 Python API 호출을 다른 엔진으로 자동 변환한다는 의미는 아니다. 새 기능의 엔진별 지원 제공 방식과 미지원 처리 방식은 설계에서 결정한다.
- 등록용 딕셔너리는 사용자가 제시한 확장 방식의 예시다. 구체적인 딕셔너리 구성·함수 인터페이스·폴더·Recipe 스키마는 비교 설계 후 확정한다. 기능 추가를 위해 기존 공통 실행 코드나 UI의 Task별 분기를 계속 추가하는 구조는 피한다.

## 확정: Sim2Real 기준 환경과 초기 배치의 구분

최종 목적은 Sim2Real이다. Builder는 실제 로봇·카메라·주변 작업 환경을 시뮬레이션에 재현하며, Workbench의 Recipe가 이 기준 환경을 임의로 변경해서는 안 된다.

| 구분 | 책임과 변경 범위 |
|---|---|
| Builder 기준 데이터 | 실제 환경을 나타내는 Scene, 로봇·카메라·주변 물체, Geometry·Physics·Calibration·좌표계 및 관련 근거를 보존한다. |
| Task 작업 대상 | Builder Metadata에 정의된 작업 대상 물체 중 이번 실행에 생성할 물체를 Recipe 목록으로 선택한다. 목록에 없는 작업 대상 물체는 생성하지 않는다. |
| Recipe 설정 | 허용된 작업 대상의 초기 위치·자세, Random Reset 범위와 단계별 실행 조건을 설정한다. 기준 Scene 원본은 수정하지 않는다. |
| Task 전용 기능 | 기존 제공 기능으로 표현할 수 없는 성공 판정·Reset 등은 개발자가 Python 함수로 추가하고 등록한다. |

- 첫 구현에서는 v8의 로봇 베이스·카메라·테이블·Cup 등 기준 환경을 유지하며, 작업 대상 블록의 사용 여부와 초기 배치 설정에 집중한다. 환경 전체를 자유롭게 편집하는 범용 Scene Editor는 만들지 않는다.
- 작업 대상 물체 목록은 생성 목록이다. 예를 들어 Builder가 `red_block`, `blue_block`, `green_block`을 정의했다면 Recipe에 `red_block`만 지정할 때 빨간 블록만 생성하고, `red_block`과 `blue_block`을 지정하면 두 블록만 생성한다. 선택하지 않은 블록을 방해 물체로 자동 유지하거나 별도의 제외 목록을 요구하지 않는다. 이 ID들은 설명용 예시이며 실제 실행에서는 Builder Metadata의 정확한 ID를 참조한다.
- 위 생성 목록은 작업 대상 물체에 적용한다. 목록에 없는 로봇·카메라·테이블·Cup 등 기준 환경을 함께 제거한다는 의미가 아니며, Builder 원본 Scene도 변경하지 않는다.
- 배치 설정은 실제로 구현 가능한 작업 영역, 충돌, 물체 크기 등의 제약을 고려해야 한다. 검증 방식과 부적합 배치 처리 정책은 후속 설계에서 결정한다. 기하학적 유효성을 실제 로봇의 도달·파지 가능성 검증과 혼동하지 않는다.
- 설정한 환경에서 Teleoperation, Source, Annotation, DataGen, Training, Simulation Evaluation을 연결할 수 있어야 한다. 일반 LeRobot 학습의 독립 사용 요구도 유지한다.
- 기존 v8의 기본 배치·Calibration을 보존한다. Recipe에 변경 설정이 없을 때의 동작은 기존 경로와 비교하여 설계하며, 아래에서 명시적으로 승인한 `four_anchors` 제외 외에는 임의로 변경하지 않는다. 기존 경로의 Random Reset을 정적 Builder 배치로 일괄 대체하지 않는다.
- 향후 서랍·문처럼 Task에 필요한 가동 요소를 지원할 수 있어야 한다. 첫 구현에서 주변 환경을 고정하는 범위와, 모든 미래 Scene 요소를 영구적으로 정적으로 취급하는 제약을 구분한다.

## 확정: Random Reset은 영역 전체의 무작위 배치 사용

- Recipe에서 생성 대상으로 선택한 물체별 초기 배치 방식을 선택한다. 랜덤 배치를 지정하면 허용 영역에서 무작위 위치를 생성하고, 특정 position을 지정하면 그 위치에 생성한다. 두 방식 모두 기존 작업 영역·물체 크기·배치 유효성 제약을 따른다.
- Data Curation으로 데이터가 부족한 영역을 확인한 뒤, 사용자가 해당 영역의 특정 위치를 Recipe에 직접 지정해 추가 시연·생성 데이터를 수집할 수 있어야 한다. 배치 설정을 위해 공통 실행 Python을 수정할 필요가 없어야 한다.
- Curation의 작업 영역 내 물체 위치 분포 표시를 유지하고, 부족한 위치는 사람이 보고 판단한다. 이후 Source 또는 DataGen에서 사용자가 생성 위치를 직접 입력한다. 부족 영역 자동 탐지·추천, Curation에서 생성 설정으로의 자동 연결은 요구하지 않는다. 추가 제안했던 부족 영역 전용 랜덤 범위 기능도 이번 요구사항에 추가하지 않는다. 기존에 합의한 일반 Random Reset 범위 설정과는 구분한다.
- Source의 추가 시연 수집과 DataGen의 새 Episode 생성에서 이 배치 의도를 표현할 수 있어야 한다. 위치 지정은 초기 상태 설정이며, Task 수행 성공이나 DataGen의 IK·물리 성공을 보장하지 않는다. 기존 Annotation의 기록 상태 복원 의미는 변경하지 않는다.
- 사용자 지시에 따라 새 프로젝트의 Reset 기능에서 `four_anchors`를 제외한다. 네 기준점 주변에 배치하는 방식은 이관하지 않는다.
- 기존 `WorkspaceRandomizer.sample()`의 `uniform` 분기를 기준으로, 허용 영역 전체에서 X/Y 위치를 균일하게 추출한다. 물체 크기·가장자리 여유를 반영한 범위, 물체 간 간격 검사, 지지면 기준 생성 높이는 유지한다. 이는 위치 무작위화이며 임의 회전까지 포함한다는 뜻은 아니다.
- `edge_uniform`은 기존 uniform의 margin을 0으로 설정하는 변형이다. 별도 공개 선택지 유지 여부와 기본 margin·Recipe 생략값은 아직 미정이다.
- `four_anchors` 제외는 승인된 배치 분포 변경이다. 기존 four-anchor 실행과 새 uniform 실행의 초기 위치·성공률이 같다고 주장하지 않는다. 성공 판정 계산과 Calibration 보존 요구는 그대로 유지한다.
- 기존 프로젝트의 코드·v8 task.json·기록은 변경하지 않는다. 과거 데이터의 Reset metadata를 uniform으로 바꾸거나 재해석하지 않는다. 과거 재현 방식은 마이그레이션 설계에서 구분한다.

## 확정: 기존 UI·기능 보존과 내부 구조 재설계

- 이번 프로젝트의 목적은 기존에 복잡하게 누적된 구현을 정돈하여 이해·유지보수·확장하기 쉬운 구조로 재설계하는 것이다. 기존 코드 구조를 그대로 유지할 필요는 없다.
- 기존 UI의 모양과 제공 기능을 보존하되, 단계별 동작 설정 방식은 최신 합의인 Recipe 중심 방식으로 전환한다. 이전 설정 폼·체크박스를 그대로 유지해야 한다는 뜻은 아니다. 초기 요청의 UI 전체 재설계 방향은 이 요구로 갱신하며, 내부 구조 정리를 이유로 화면을 임의로 새로 디자인하거나 기존 실행·검토 기능을 누락하지 않는다.
- UI는 Scene·Recipe 선택, 실행·중지 등 조작, Preview·진행·로그·결과 및 Curation 확인을 담당한다. 새 Task 함수 추가 때마다 해당 함수 전용 UI 설정을 구현하도록 요구하지 않는다.
- Recipe 입력은 두 방식을 모두 지원한다. 외부 파일 불러오기 버튼으로 기존 Recipe를 열 수 있고, UI 내 코드 편집기에서 Recipe를 작성·수정할 수 있다.
- UI 편집기로 작성한 Recipe도 외부 Recipe 파일을 보관하는 동일한 저장 위치에 파일로 저장한다. UI 내부에만 보관되는 별도 설정으로 분리하지 않는다. 실제 저장 디렉터리, 파일명, 기존 파일 수정·다른 이름 저장 정책은 후속 설계에서 결정한다.
- 실행 입력은 저장된 Recipe 파일이다. 사용자는 편집 내용을 먼저 저장하고, 실행기는 그 파일을 다시 읽고 검증한 뒤 실행한다. 편집기의 미저장 버퍼를 직접 실행하거나 실행 버튼이 수정 내용을 암묵적으로 저장·실행하지 않는다.
- 편집기에 미저장 수정이 있으면 저장 필요 상태를 표시하고 실행을 막아 먼저 저장하도록 안내한다. 새 Recipe는 파일로 저장한 후 실행할 수 있다. 실행 전 읽어 확정한 Recipe 내용과 이후 편집 내용은 구분한다.
- 실제 실행에 사용한 설정 내용은 시스템이 결과 기록에 자동으로 남긴다. Recipe 경로만 기록하는 것으로 대체하지 않으며, 이후 원본 Recipe가 수정되어도 과거 실행 설정을 확인할 수 있어야 한다. 사용자가 별도의 Recipe 사본을 만들거나 관리할 필요는 없다. 기록 형식과 저장 구조는 설계 단계에서 결정한다. 설정 기록만으로 사용자 함수·외부 의존성까지 완전한 재현성이 보장된다고 주장하지 않는다.
- UI와 연결된 기능·사용 흐름을 기존 구현에서 조사하여 보존 목록을 마련한다. 정확한 시각적 동등성 기준과 개별 화면 변경 허용 범위는 아직 확정하지 않았다.
- 기존 화면을 픽셀 단위로 복제하거나 모든 위젯을 유지할 필요는 없다. 새 Recipe 중심 구조에서 불필요해진 설정 UI와 이를 위한 중복 연결 코드는 제거할 수 있다. 사용자 예시인 오른쪽 Scene objects 체크박스, Active Objects 표시, Task preset, Pick object, Target cup 등 기존 Task/Object 설정 폼은 Recipe로 대체할 수 있다. 필요한 실행 정보는 별도의 읽기 전용 요약으로 보여줄 수 있으나 그 구체적 구성은 아직 미정이다.
- 위 제거 허용은 기존 프로젝트 원본 수정이나 핵심 기능 삭제 지시가 아니다. 물체 선택·Task 설정 등 실제 기능은 Recipe에서 계속 제공하며, 실행·중지·Preview·로그·결과 확인·Curation 등 필요한 기능은 보존한다. 다른 UI 요소도 새 구조에서 필요한 역할을 확인해 유지·대체·제거를 판단한다.
- UI, 단계별 실행, 데이터 처리, 엔진별 구현의 책임을 명확히 하여 기능 추가·수정·삭제의 영향 범위를 제한하고 회귀 오류를 줄인다. 오류가 전혀 발생하지 않는다는 보장으로 해석하지 않으며 관련 동작 검증으로 뒷받침한다.
- 기능을 추가·수정·삭제하기 쉬운 구조는 설계 목표이며, 현재 기존 기능을 삭제할 권한을 의미하지 않는다. 이미 명시적으로 승인된 four_anchors 제외·Recipe 동작 변경·DataGen 고정 DLS + Best Effort 및 SciPy IK/Strict/Hold 이관 제외는 별도 합의로 유지한다.
- 폴더·모듈·클래스·의존성·내부 호출 구조는 변경할 수 있다. 사용자에게 보이는 동작과 기존 계산 의미의 변경은 구조 변경과 구분하여 합의한다.

## 확정: 전체 기능 이관 범위와 알고리즘 보존 경계

- MiniVLA는 사용자 승인에 따른 명시적 제외 대상이다. 아래 전체 기능 보존·기존 Dataset/Policy 사용 요구는 MiniVLA 모듈·호환 계층·Checkpoint 로더·추론/평가·모델 전용 데이터 변환의 이관을 요구하지 않는다. 기존 원본 보존 의무는 유지한다.

- 새 플랫폼은 기존 UI 각 영역의 역할과 기능을 유지하며 새 코드베이스·아키텍처로 다시 구현한다. 첫 기준 환경을 v8 Pick & Place로 정한 것은 제품 기능을 Source·Simulation Evaluation 일부로 축소한다는 뜻이 아니다.
- 필수 이관 범위에는 Real2Sim Capture, Real/Sim, Work Pipeline, Precision Calibration, Data Curation, Source Demo, Annotation, DataGen, Dataset Conversion, Policy Training, Offline Validation, Simulation Evaluation, Dataset·Policy Hub 업로드/다운로드, 실제 로봇 평가가 포함된다. 각 영역의 세부 기능은 기존 구현을 조사해 목록화하며, 여기의 열거를 이유로 기존 세부 기능을 임의로 제외하지 않는다.
- 기존 구현은 기능·동작·알고리즘의 Reference Implementation으로 사용한다. 공식, 계산 순서 중 결과에 영향을 주는 부분, 단위·좌표 의미, threshold, 시간·상태 조건 및 판정 결과를 보존한다.
- 기존 파일 전체나 의존성 그래프를 복사해야 한다는 요구는 아니다. 어느 모듈에서 값을 받아오는지, 인자 전달 경로, 클래스·함수 배치, 내부 호출 규칙, Metadata 접근 방식은 새 아키텍처에 맞게 재설계할 수 있다.
- 바꿀 수 있는 데이터 전달 규칙과 보존해야 하는 데이터 의미를 구분한다. 예를 들어 관측/명령 구분, 좌표 변환 순서, pre/post-step 시점, 보정 중복 적용 방지, 장치 제어 제한, 저장된 기록의 해석처럼 실제 동작에 영향을 주는 조건은 단순한 내부 연결 방식으로 취급해 제거하지 않는다.
- 기능이 기존 코드에 존재한다는 사실과 실제 검증 완료 여부는 구분한다. 재구현 후 기능별 검증을 수행하며, 특히 실제 로봇 평가는 필수 기능 범위이지만 현재 실물 검증 완료를 의미하지 않는다.

## 확정: 단계별 독립 실행과 LeRobot 상호운용

- Workflow는 강제 순차 실행 절차가 아니다. 각 단계는 필요한 입력을 사용자가 선택하고 해당 단계의 Recipe로 독립 실행한다. 이전 단계가 같은 세션이나 이 프로젝트에서 실행됐다는 이력을 요구하지 않는다.
- Source Demo는 사용할 Scene과 Metadata를 선택하고 Recipe로 생성할 작업 물체·초기 배치 등 시뮬레이션 환경을 구성하여 시연을 수집한다.
- Annotation은 필요한 Source Demo Dataset이 있으면 실행할 수 있다. 기존 자료 또는 새로 수집한 자료를 선택할 수 있으며 Source 직후 Annotation을 강제하지 않는다.
- DataGen은 필요한 Annotation 정보가 포함된 Dataset을 선택해 실행한다. Annotation 실행 이력 자체가 아니라 실제 입력 데이터의 형식·정보와 실행에 필요한 환경 호환성을 확인한다.
- Training은 공식 LeRobot이 지원하고 선택 Policy와 호환되는 Local 또는 Hub Dataset으로 바로 실행할 수 있어야 한다. 프로젝트에서 만든 Dataset, Workspace, Task Recipe나 프로젝트 전용 provenance를 일반 학습의 필수 조건으로 요구하지 않는다.
- 프로젝트의 Dataset 변환 결과는 다른 사용자도 공식 LeRobot 도구로 사용할 수 있어야 한다. 부가 Metadata가 있어도 일반 Dataset 사용을 프로젝트 전용 Reader나 실행기에 종속시키지 않는다.
- 외부 Dataset으로 학습하고, 외부 Policy를 가져오며, 만든 Dataset·Policy를 공유할 수 있어야 한다. 학습·Dataset 처리·모델 로딩·Hub 기능은 공식 LeRobot CLI/API 및 관련 공식 라이브러리가 제공하는 기능을 우선 사용하고 불필요한 전용 구현을 만들지 않는다.
- 상호운용은 모든 Dataset과 모든 Policy의 무조건적 조합을 뜻하지 않는다. 공식 형식·버전·feature·Policy 요구사항은 확인한다. Simulation/실물 평가에서는 로봇 action·관측·카메라·좌표 등 실행 호환성을 별도로 검사하되, 이를 외부 Dataset 일반 학습의 불필요한 제약으로 확대하지 않는다.
- 각 단계의 구체적인 입력 계약과 실행에 필요한 Scene 참조 방식은 설계에서 정한다. 단계 독립성을 위해 기록된 초기 상태·Calibration·판정 의미 등 필요한 정보를 버리거나 추측하지 않는다.

## 확정: 엔진 지원 검사와 Scene v8 즉시 사용 범위

- Recipe가 참조한 기능이 선택한 엔진에서 지원되지 않으면 실행 전에 원인과 미지원 기능을 표시하고 실행을 막는다. 다른 함수·판정·엔진으로 암묵적으로 대체하지 않는다.
- Scene v8의 기존 기능은 사용자가 Task 함수나 엔진 연결 코드를 추가로 작성하지 않아도 바로 사용할 수 있도록 제공한다. 기존 Pick & Place 함수, Reset, 단계별 성공·실패 판정과 필요한 연결을 신규 구조에서 구현한다.
- 엔진을 사용하는 v8의 Source, Annotation, DataGen, Simulation Evaluation 및 관련 Real/Sim 기능은 Isaac Lab과 MuJoCo 양쪽에서 사용할 수 있어야 한다. 한 엔진만 완성하거나 다른 엔진을 미지원으로 표시하는 것으로 v8 이관을 완료했다고 판단하지 않는다.
- Capture, Calibration, Curation, Dataset 변환, Training, Hub, 실제 로봇 평가도 이미 합의한 전체 기능 범위대로 제공한다. 엔진 독립 기능을 불필요하게 두 벌 구현한다는 뜻은 아니다.
- 향후 새 Scene·Task에 기존 기능으로 표현할 수 없는 동작이 필요하면 개발자가 함수를 추가한다. 이 확장 절차를 현재 v8 기능을 사용자에게 미완성 상태로 넘기는 근거로 삼지 않는다.
- v8은 양 엔진의 기능별 실행·입출력·기존 계산 의미를 검증한 상태가 완료 목표다. 현재 기존 코드의 존재나 과거 기록을 모두 검증 완료로 간주하지 않는다. 누락·실패가 발견되면 원인과 영향을 보고하고 보존 원칙 아래 해결하며, 실패를 숨기거나 판정 조건을 완화하지 않는다.
- 양 엔진 지원 완료는 모든 Episode의 작업 성공이나 엔진 간 물리·픽셀 완전 일치를 보장한다는 뜻이 아니다. 정상적인 Task 실패와 구현 오류·미지원 상태를 구분하여 기록한다.

## 확정: 새 데이터 계약을 기준으로 기존 자료 변환

- 기존 Dataset, Policy, Scene, Calibration 및 관련 실행 자료를 새 플랫폼에서 사용할 수 있어야 한다. 다만 기존 저장 형식에 새 아키텍처를 맞추거나 과거 Metadata 구조를 계속 유지하는 것이 목표는 아니다.
- 새 코드베이스의 책임 분리·구현·데이터 읽기 계약을 먼저 설계하고, 기존 자료를 그 계약에 맞게 변환한다. 새 플랫폼에서 사용하는 데이터는 새 계약을 따른다. 직접 읽기나 호환 계층이 필요한지는 설계에서 판단하며 영구적인 Legacy 형식 지원을 기본 요구로 삼지 않는다.
- 변환 결과에서는 더 이상 필요하지 않은 내부 구조·중복·필드를 제거할 수 있고, 새 계약에 필요한 정보를 추가할 수 있다. 기존 필드를 전부 복사하는 것을 보존의 기준으로 삼지 않는다.
- 삭제 가능 여부는 새 계약에서의 역할과 실제 의미를 조사해 판단한다. Calibration 증거, 좌표·단위·변환 순서, 관측/명령 구분, 기록 시점, 기존 판정 및 재현에 필요한 정보는 형식 정리 과정에서 손실시키지 않는다. 과거 Reset 의미도 다른 방식으로 다시 이름 붙이지 않는다.
- 추가 정보는 기존 코드·자료에서 확인하거나 검증 가능한 방식으로 도출한다. 근거가 없는 값이나 검증 상태를 만들어 채우지 않으며, 확보하지 못한 필수 정보는 명시적으로 보고한다.
- 기존에 합의한 원본 보존은 유지한다. 새 시스템의 실제 사용 데이터는 변환·정리하되 기존 원본은 비교·복구 근거로 보존하고, 변환 결과의 구조·수치·동작을 검증한다. 현재 단계에서는 변환이나 삭제를 실행하지 않는다.
- LeRobot Dataset·Policy의 공식 상호운용 요구는 유지한다. 새 내부 계약을 이유로 공식 형식을 임의로 깨뜨리거나 외부 LeRobot 자료에 프로젝트 전용 규칙을 강요하지 않는다.

## 확정: C안 — 가치 있는 공통 처리와 엔진별 공식 실행 구조

- 공통 처리와 엔진별 실행을 분리하는 C안을 기본 아키텍처 방향으로 확정한다.
- Isaac Lab은 SceneCfg·EnvCfg·MDP Terms 등 공식 구성 방식을, MuJoCo는 MjModel/MjData 등 공식 API를 최대한 활용한다.
- Recipe 해석, Object ID 참조, 재사용 가능한 Task 판정 계산, 데이터 기록 등 실제 공유 가치가 있는 부분만 공통화한다.
- Source·Annotation·DataGen 등의 실행 과정을 하나로 통합하는 것을 요구하지 않는다. 엔진별 구현이 더 단순하면 분리하며, 호출 시점·상태 수명·데이터 의미는 명시한다.
- 불필요한 Interface·Adapter·Wrapper·추상 클래스나 범용 Env를 의무적으로 추가하지 않는다. 문서의 계약 명시가 반드시 별도 Python 추상 계층을 뜻하지는 않는다.
- 기존 v8의 Calibration, 성공 판정 알고리즘, 단계별 판정 조합 및 실행 시점을 그대로 보존한다. 공식 구조를 적용하거나 공통화하기 위해 기존 의미를 바꾸지 않는다.
- 구체적인 파일 배치와 데이터 스키마는 후속 비교·합의 대상이다. 제품 간 연결의 기본 방향은 다음 합의를 따른다.

## 확정: 독립 프로젝트와 Scene 패키지 기반 연결

- Builder와 Workbench는 독립적인 프로젝트로 유지한다. Builder가 생성한 Scene 패키지를 Workbench가 읽어 사용하며, Workbench가 Builder 내부 구현에 직접 의존하지 않는다.
- 좌표 변환·Metadata 검증 등 양쪽에서 동일하게 사용하는 코드만 실제 필요성과 의존성을 확인한 뒤 공통화할 수 있다. 처음부터 큰 공통 라이브러리를 만들지 않는다. 공통 코드의 패키징·배포 형태는 아직 미정이다.
- Scene 패키지는 새로운 Task 함수 구현에 필요한 Object ID, Geometry, Joint, 좌표계 및 엔진별 참조 정보를 제공한다. 구체적인 필드와 파일 배치는 후속 설계에서 정한다.
- Builder가 생성한 Calibration 데이터와 적용 의미를 Workbench에서도 정확히 유지한다. 기존 v8과 외부 참조 Asset, Calibration 적용 로직을 함께 보존한다. 데이터 파일만 전달하고 적용 순서·좌표·단위·모델 identity 등을 잃어버려서는 안 된다.
- 원본 보존 원칙을 유지한다. 패키지 구성 및 참조 경로를 새 계약에 맞게 변환하더라도 필요한 자산과 의미를 누락하지 않는다. 현재 단계에서는 데이터 변환이나 구현을 실행하지 않는다.

## 확정: Task 파일별 등록 선언과 명시적 로딩 목록

- 각 Task Python 파일에서 필요한 함수와 등록 정보를 함께 관리하며, 별도의 명시적 로딩 목록으로 연결한다.
- 새로운 Task는 Task 파일 작성과 로딩 목록 등록으로 Recipe에서 선택할 수 있어야 한다. 기존 공통 실행 코드나 UI에 Task별 분기를 추가하지 않는다.
- 단순 기능은 일반 Python 함수를 그대로 사용한다. 등록을 위해 불필요한 클래스·Wrapper·복잡한 플러그인 구조를 요구하지 않는다.
- StableGrasp처럼 상태가 필요한 기능에만 상태 관리 구조를 사용한다. 기존 상태 초기화·누적·tick 처리·latch·판정 시점을 보존한다.
- 등록 선언의 정확한 문법, 로딩 목록 위치와 파라미터 계약은 후속 설계한다. 새로운 센서 등 기존 엔진 기능으로 제공되지 않는 입력이 필요할 때는 해당 기능 구현도 필요하며, 이를 Task별 공통 실행/UI 수정과 구분한다.

## 확정: 선언용 YAML Recipe

확정일: 2026-10-25.

- Recipe는 사용자가 직접 편집하고 주석을 작성할 수 있는 YAML 파일로 작성한다.
- YAML은 실행 설정을 선언하는 용도로만 사용한다. 실제 계산과 조건 판정은 등록된 Python 함수가 수행한다.
- 실행 전에 필드, 값 타입, Scene Object ID, 등록 함수 이름과 파라미터를 검증한다. 잘못된 설정은 명확한 오류로 안내하고 실행을 막는다. 기존 엔진 지원 검사 요구도 유지한다.
- 불필요하게 복잡한 YAML 기능이나 자체 설정 언어를 만들지 않는다.
- 이 결정은 Recipe 파일 형식에만 적용한다. Scene Metadata와 결과 기록 형식, 구체적인 Recipe 필드 구성은 별도로 검토한다.

## 확정: 단계별 Recipe 구성과 UI 편집 관계

확정일: 2026-10-25.

- 한 Recipe 파일에는 하나의 실행 단계만 정의한다. stage, engine, inputs, objects, functions, execution, output 구분을 기본 방향으로 채택하며, 정확한 필드명·기본값은 상세 설계에서 정한다.
- 각 단계에 필요한 필드만 사용한다. Scene의 Geometry·Calibration·Object 기준 정보는 Builder Metadata와 연결된 Scene 패키지에서 가져오며 Recipe에 중복 정의하지 않는다.
- stage는 UI의 단계 구분과 별도로 Recipe에도 유지한다. CLI 독립 실행과 잘못된 단계의 Recipe 실행 방지에 사용한다.
- 시뮬레이션 단계의 엔진은 UI에서 Isaac Lab/MuJoCo로 선택할 수 있다. UI에서 변경하면 Recipe 편집 내용에 반영하며, 사용자가 명시적으로 저장한 YAML을 실행기가 다시 읽어 실행한다.
- UI의 엔진 변경은 미저장 편집으로 취급한다. 저장 전 실행을 막고, 저장된 Recipe와 별개의 숨은 UI 엔진 값으로 실행 설정을 덮어쓰지 않는다.
- Training 등 시뮬레이터가 필요 없는 단계에는 engine을 요구하지 않는다.
- UI는 Recipe를 편리하게 편집하는 인터페이스다. 실제 실행 설정의 기준은 저장된 Recipe 파일이며, Recipe로 시뮬레이터 내부 구현까지 관리하지 않는다.
- Annotation의 기록된 초기 상태 복원과 단계별 기존 성공 판정 의미·실행 시점을 유지한다.

## 확정: Metadata 좌표계 지정과 실행기 변환

확정일: 2026-10-25.

- 위치 입력에는 Builder Metadata에 정의된 좌표계 ID를 명시한다.
- 주로 Workspace 좌표계를 사용하되 World 등 Builder Metadata에 정의된 다른 좌표계도 선택할 수 있다. 실제 ID·원점·축은 Metadata를 따른다.
- 실행기가 Metadata의 Transform으로 좌표 변환을 처리한다. 사용자에게 수동 변환을 요구하지 않는다.
- Curation에서 물체 위치를 표시할 때 좌표계와 단위를 명확히 보여주어 사용자가 확인한 위치를 Recipe에 입력할 수 있도록 한다. 부족 영역 자동 판단이나 Recipe 자동 생성 기능을 추가하는 결정은 아니다.
- 좌표계 ID가 없거나 필요한 변환을 수행할 수 없으면 실행 전에 명확한 오류를 안내하고 실행을 막는다. 임의 좌표계나 identity 변환으로 대체하지 않는다.
- 기존 v8의 좌표계, Calibration 적용 방식·단위·변환 순서를 보존한다. 고정 배치의 높이 입력 방식과 자세 표기는 별도로 설계한다.

## 확정: 충돌 Geometry 기반 작업면 배치

- Fixed XY와 Random XY 모두 작업면 접촉 배치를 기본 방향으로 삼는다. 사용자는 작업면 기준 위치를 지정하거나 랜덤 생성을 선택하며 Z를 직접 계산할 필요가 없어야 한다.
- 실행기는 Builder Metadata와 연결된 실제 충돌 Geometry, Geometry의 물체 원점에 대한 Transform, 배치 자세, 작업면 정보를 이용해 생성 위치를 계산한다. 물체마다 다른 크기·형상·원점을 지원하도록 설계하며 `높이 / 2`를 일괄 가정하지 않는다.
- 중심 원점 직육면체뿐 아니라 바닥 원점과 다른 형상도 고려한다. 지원 형상·작업면의 구체 범위와 계산 방법은 상세 설계에서 검증한다. 정보가 부족한 경우 단순 bounding box로 조용히 대체하지 않는다.
- 기존 v8의 높이 계산과 배치 동작은 보존한다. 새 접촉 배치와 기존 생성 여유·초기 상태의 차이를 수치 및 엔진별 동작으로 검증하고, 차이의 원인과 영향을 보고한다. 기존 v8을 접촉 간격 0으로 임의 변경하지 않는다.
- Annotation의 기록 초기 상태를 새 접촉 배치로 다시 계산하지 않는다. XYZ 직접 지정 기능의 제공 여부는 이번 합의로 확정하지 않는다.

## 확정: 배치 자세의 기본값과 높이 계산

확정일: 2026-10-25.

- 배치 자세를 생략하면 Builder Metadata에 정의된 해당 물체의 기본 자세를 사용한다. 다른 자세를 원할 때만 Recipe에서 명시적으로 지정한다.
- Fixed XY와 Random XY에 같은 원칙을 적용한다. 불필요한 자세 랜덤화 기능은 현재 범위에 추가하지 않는다.
- 자세가 변경되면 해당 자세와 충돌 Geometry를 기준으로 생성 높이를 계산한다. 기본 자세에서 계산한 높이를 그대로 재사용하지 않는다.
- Metadata 기본 자세의 좌표 의미를 유지하고 필요한 Transform을 적용한다. Recipe 위치의 좌표계를 선택했다는 이유로 기본 자세의 숫자를 해당 좌표계 자세로 재해석하지 않는다.
- 기존 v8의 3mm 생성 여유와 기존 배치 동작은 보존하며, 새로운 배치 계산과 구분해 검증한다. 승인된 four_anchors 제외는 유지한다. Annotation의 기록 상태 복원은 이 기본값으로 덮어쓰지 않는다.
- 자세의 정확한 YAML 표기와 부적합 배치 처리 정책은 후속 설계한다.

## 확정: 부적합 배치 차단과 제한된 재추출

확정일: 2026-10-25.

- Fixed XY는 사용자가 지정한 위치를 임의 변경하지 않는다. 작업 영역 이탈이나 다른 물체와의 겹침이 있으면 원인을 안내하고 실행을 막는다.
- Random XY는 허용 영역과 기존 배치 조건을 유지하며 정해진 횟수 안에서 유효 후보를 재추출한다. 한도 내에 배치하지 못하면 원인을 알린다.
- 위치 보정이나 허용 영역 자동 확장은 하지 않는다.
- 기존 v8의 배치 검사·재시도 조건과 동작을 코드에서 확인해 보존한다. 새로운 Geometry 기반 검사와의 차이가 있으면 별도로 보고하고, 새 방식을 동일한 기존 동작이라고 간주하지 않는다.
- 재추출 한도와 소진 시 처리는 아래 확정 정책을 따른다. 실행 중 Random 배치는 해당 Episode 시작 전에 검사하며, 모든 미래 배치를 최초 실행 전에 검증했다는 의미는 아니다.

## 확정: 초기 배치 1,000회 소진 시 작업 중단과 데이터 보존

확정일: 2026-10-25.

- Random XY는 기존 물체별 후보 추출 한도인 1,000회를 유지한다. 한도를 소진하면 해당 실행 작업을 중단하고, 이미 정상적으로 저장된 Episode는 보존한다. 실패한 물체를 건너뛰어 실행을 계속하거나 한도를 자동 초기화해 무한 재시도하지 않는다.
- 미완료 Episode를 성공 데이터로 저장하지 않는다. 어떤 물체가 어떤 배치 조건에서 몇 번 실패했는지 원인을 기록한다.
- 이 정책은 초기 배치 실패에만 적용한다. 정상 배치 이후의 Grasp 실패·Task 실패와 DataGen 재생성 정책은 기존 동작을 유지한다.
- 기존 Resume 기능과 데이터 저장의 안전성을 보존한다. 기존 단계별 지원 범위·완료 처리·중복 방지·복구 조건을 조사해 이관하며 모든 단계의 임의 시점 Resume가 이미 구현되어 있다고 가정하지 않는다.
- 기존 엔진별 상위 호출부의 예외 처리와 새 작업 중단 정책의 차이는 별도로 확인·보고한다. 새 저장/Resume 구현이나 검증이 완료된 것은 아니다.

## 확정: 새 데이터 계약에 따른 JSON Scene Metadata

확정일: 2026-10-25.

- 사용자가 작성하는 Recipe는 YAML, Builder가 생성하고 Workbench가 읽는 Scene Metadata는 JSON으로 구분한다.
- 기존 Metadata 파일 구조를 그대로 복사하지 않는다. 새 데이터 계약을 기준으로 필요한 정보를 명확히 구성하고 중복 데이터·불필요한 필드를 최소화한다. 모든 정보를 하나의 거대한 JSON에 넣지 않는다.
- 실제 Scene 실행과 Task 구현에 필요한 Object ID, Geometry, Transform, Joint, Calibration 적용 정보와 검증 상태를 보존한다. 데이터 정리를 이유로 계산 의미나 적용 근거를 제거하지 않는다.
- USD·MJCF·Mesh 등의 Asset은 별도 파일로 유지하고 Metadata에서 참조한다. 외부 참조 Asset 보존 요구도 유지한다.
- 기존 v8과 Calibration 데이터를 새 형식으로 변환하더라도 정확한 계산 의미·적용 방식·단위·좌표·변환 순서가 달라지지 않아야 한다. 원본은 보존하며 변환 결과를 검증한다.
- 책임별 파일 구성·구체적 필드·참조 규칙은 후속 설계한다. 결과 기록과 Dataset 형식은 이번 결정에 포함하지 않는다.

## 확정: Metadata 책임 구분과 단순한 파일 구조

- Scene Metadata의 책임을 구분하고 `scene.json`을 패키지 진입점으로 사용한다.
- 제안된 다섯 JSON 파일을 각각 생성해야 한다는 뜻은 아니다. 실제 데이터 크기·참조 관계·변경 주기·각 모듈의 사용 방식을 확인해 가장 단순한 파일 개수와 구성을 결정한다.
- 동일한 정보를 여러 Metadata 파일에 중복 저장하지 않는다. 조회를 위한 불필요한 파일 참조 단계나 변환 과정을 만들지 않는다.
- Calibration 원본·적용 의미·근거와 검증 상태를 보존한다. Asset과 Metadata의 참조 관계 및 이식성을 보장하도록 계약을 설계한다.
- 기존 v8의 Metadata 구조를 복제하지 않고 새 계약을 설계한다. 구체적인 파일 분할은 후속 설계 대상이며, 현재 데이터 파일을 생성·변환하지 않는다.

## 확정: 실행 Asset을 포함한 이동 가능한 Scene 패키지

확정일: 2026-10-25.

- Builder가 생성한 Scene 패키지는 필요한 시뮬레이터·라이브러리가 설치된 다른 경로나 컴퓨터에서도 사용할 수 있어야 한다.
- USD·MJCF·URDF·Mesh·Texture·Collision Geometry·Calibration 적용에 필요한 파일 등 실제 실행 의존성을 조사해 패키지에 포함한다. 기존 v8의 외부 Finger Collision 데이터와 보정된 Robot Asset도 누락하지 않는다.
- 실행에 필요한 참조는 패키지 내부 상대 경로로 연결한다. 각 Asset 형식의 상대 경로 해석 규칙을 유지하며 원본 컴퓨터의 절대 경로나 패키지 밖 파일에 숨은 의존성을 남기지 않는다.
- 원본 촬영 자료·Calibration 실험 증거를 모두 실행 패키지에 넣을 필요는 없다. 실행에 필요한 데이터와 보존·추적용 원본 자료를 구분하며, 원본 보존 의무는 유지한다.
- Asset 중복을 최소화한다. 패키지를 이동한 뒤 참조 파일 누락과 무결성을 검증할 수 있어야 한다. 동일 파일의 무결성과 계산·물리 동작의 동등성 검증은 구분한다.
- 기존 원본 Scene과 데이터는 수정하지 않고 새 패키지를 별도로 생성한다. 현재 설계 단계에서는 패키지 생성·복사·참조 재작성을 실행하지 않는다.

## 확정: 원본 자료 추적과 실행 의존 분리

- 원본 자료는 ID, SHA-256 해시, 보존 위치로 추적한다. 불필요한 별도 데이터베이스나 복잡한 관리 시스템을 만들지 않는다.
- 실행에 필요한 Calibration과 Asset은 Scene 패키지에 포함한다. 원본 촬영 이미지·실험 증거 등 추적·재검토 목적의 자료는 외부에 보존할 수 있다.
- 외부 원본에 접근할 수 없어도 실행 필수 데이터가 완전하면 시뮬레이션 실행을 막지 않는다. 원본 접근 상태는 명확히 표시한다.
- 원본 접근 상태와 검증 상태를 구분한다. 접근 불가를 검증 완료로 해석하지 않으며 기존 v8의 검증 상태를 그대로 유지한다.
- Metadata는 필요한 정보만 간결하게 구성하고 중복 기록을 최소화한다. 원본 보존과 필요한 증거 재검토 의무는 유지한다.

## 확정: 실행 Scene Revision 보존과 기록 고정

- Builder의 편집 작업과 실행용 Export를 구분한다. Scene 또는 Calibration을 변경해 Export하면 기존 패키지를 덮어쓰지 않고 새로운 Revision을 생성한다.
- Workbench의 Source·Annotation·DataGen·Evaluation 및 Scene을 사용하는 관련 실행 기록에 실제 사용한 Scene ID, Revision, 무결성 정보를 남긴다.
- 과거 Dataset 재생과 Resume는 기록 당시의 Scene과 Calibration을 사용한다. 최신 Revision으로 자동 변경하지 않는다. 필요한 Revision이 없거나 무결성이 일치하지 않으면 명확한 오류를 안내하고 진행하지 않는다.
- 불필요한 Asset 중복 복사나 복잡한 자체 버전 관리 시스템을 만들지 않는다. 여러 실행이 같은 패키지 Revision을 참조할 수 있으며 실행마다 전체 Asset을 복사할 필요는 없다.
- 기존 scene2_builder/v8과 관련 Calibration 원본은 그대로 보존한다. Revision 관리가 원본 변환·덮어쓰기 권한을 뜻하지 않는다.

## 확정: 제품 책임·작업 프로세스·Episode와 LeRobot의 구분

확정일: 2026-10-25.

- Workbench는 Capture·Real/Sim·Precision Calibration·장치 연결/제어와 학습 Workflow·실제 로봇 평가를 담당한다. Builder는 캡처·보정 자료를 받아 Scene 재구성·Scene/카메라 정합 계산·검토·실행 패키지 Export를 담당한다.
- Calibration은 장치 의존성과 계산 책임에 맞게 배치한다. 기존 데이터·적용 로직을 정확히 보존하고 양쪽에서 실제 필요한 계산만 공유하며 중복 구현을 최소화한다.
- 기존 UI 기능을 유지하고 엔진·학습·장치 작업은 로컬 별도 작업 프로세스에서 실행한다. UI와 CLI는 저장 Recipe 실행 계약을 공유한다. 불필요한 Launcher·Wrapper·Adapter·중간 전달 계층을 추가하지 않으며 엔진 공식 실행 구조를 최대한 활용한다.
- Source·Annotation·DataGen·재생용 내부 Episode 계약과 공식 LeRobot 학습·공유 계약을 역할별로 구분한다. 불필요한 데이터 중복 저장과 자체 구현을 피하고 기존 기록·재생 의미를 보존한다. 외부 공식 Dataset 일반 학습에 내부 Episode 계약을 요구하지 않는다.
- 다음 산출물은 전체 폴더·주요 파일 책임·호출/의존 관계·데이터 계약·Workflow/UI·이관/검증 계획을 포함한 통합 설계 문서다. 세부 선택을 하나씩 질문하지 않고 구체안에서 함께 검토한다. 아직 구현 코드를 작성하지 않는다.

## 확정: MiniVLA 개발·이관 범위 제외

- MiniVLA는 새로운 플랫폼의 개발 및 이관 범위에서 완전히 제외한다. 새 Robot Learning Workbench에 관련 모듈, 호환 계층, Checkpoint 로더, 학습·추론·평가 기능을 이관하거나 구현하지 않는다.
- 새 폴더 구조에 `learning/legacy_minivla/`를 만들지 않는다. MiniVLA 전용 데이터·Checkpoint 변환이나 호환성 검증도 새 플랫폼의 완료 조건에 포함하지 않는다.
- 이 제외는 기존 기능 보존 원칙의 명시적 예외다. 기존 프로젝트에 남아 있는 MiniVLA 원본 코드·데이터·Checkpoint는 수정하거나 삭제하지 않는다.
- Policy 학습·추론은 공식 LeRobot CLI/API를 중심으로 설계한다. 현재 지원 대상으로 삼는 ACT·SmolVLA 등 공식 Policy의 학습·로딩·평가 및 공식 Dataset 상호운용 방향은 유지한다.
- 이번 변경은 설계 문서에만 적용하며 구현을 시작하지 않는다.

## 확정: 공식 LeRobot 학습과 외부 결과 조회 분리

- MiniVLA 개발 과정에서 자체 구현한 Learning Rate 그래프, Training/Validation Loss 기록·시각화 및 학습 관리 코드는 ACT·SmolVLA로 이관하지 않는다. 기존 UI 기능 보존 요구의 명시적 예외로 취급한다.
- ACT·SmolVLA 학습은 공식 LeRobot CLI/API와 Trainer의 기본 동작을 최대한 그대로 사용한다. 그래프나 UI를 위해 학습 루프·LR Scheduler·Optimizer·Validation 처리를 자체 변경하거나 확장하지 않는다.
- Loss·Learning Rate 시각화는 공식 로깅 기능을 우선 활용한다. 추가 표시가 필요할 때만 공식 로그·결과를 읽는 독립적인 조회 모듈로 구현한다. 조회 모듈이 Trainer 상태를 수정하거나 학습 콜백을 주입하지 않는다.
- Offline Validation은 별도의 입력·실행·결과를 가진 독립 단계로 유지하며 학습 엔진 내부에 삽입하지 않는다. 공식 Trainer 자체의 기본 검증 동작과 별도 Offline Validation을 구분한다.
- 공식 로그에 없는 지표를 채우기 위해 학습 내부 처리를 추가하지 않는다. 로그/시각화 오류가 학습 계산에 영향을 주지 않도록 분리한다.
- 기존 MiniVLA 원본 코드·데이터는 수정하거나 삭제하지 않는다. 현재는 설계 문서만 수정한다.

[T02](t02-pick-place.md)에서 v8 순수 판정/StableGrasp·명시 등록을 구현하고 B01 실제 입력 및 저장 phase를 오프라인 비교했다. T01 증거도 보존했으며 실제 엔진 상태 추출/MDP 연결 검증은 미완료다. [T04](t04-collision-contact.md)에서 지원 다면체/convex 평면 범위의 일반 Geometry 접촉 배치·다른 입력 frame을 구현했다. 곡면/비평면/native 변환·실제 물리 충돌은 지원/검증 완료가 아니다. ## 2026-10-26 최종 Dataset 아키텍처 결정

C: 단계별 공식 Native Dataset + 최소 실행 Metadata를 채택한다. Source/Annotation/Mimic 생성과 필요한 MuJoCo 자료는 공식 EpisodeData/HDF5, 정책 학습·실물 정책 자료는 공식 LeRobot 계약을 우선한다. 자체 Episode별 HDF5/Index/Descriptor/호환 Reader는 폐기한다. 정상 기록에 전수 배열 SHA·영상 재decode 검사를 넣지 않으며 닫힌 불변 segment staging/atomic publish로 미완료를 제외한다.

Curation은 원본과 구별되는 영구 선택/순서/half-open frame range/split JSON이며 100→80→재로드→70 재편집을 보장한다. 학습 시 정확한 선택 row만 공식 LeRobot으로 materialize하고 원 MP4 bytes/offset을 재사용한다. 원본 RGB 화질·정밀도를 낮춰 용량을 줄이지 않는다. 원본 이동/삭제는 명시 오류이며 독립 Export만 필요한 copy를 수행한다. 실제5GiB workload 없이 비증가를 보장하지 않는다. [구현·검증 및 남은 범위](native-dataset-transition.md)를 따른다.
